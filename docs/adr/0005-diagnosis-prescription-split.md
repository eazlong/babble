# 诊断层与处方层分离：summary 诊断，quest 处方

策划视图报告的"下次内容建议"由 quest-service 产出（处方层），summary-service 只产出学习诊断（诊断层），报告 = 诊断 + 处方拼接。summary-service 不内置任何内容推荐逻辑。

## 理由

每日修复令的调度（60% 复习/25% 错词/15% 新词）、词灵阁四房间轮换、时光回廊薄弱项回流——这些推荐逻辑是 quest-service 的核心职责（GDD 已归 quest）。若 summary 也算一遍，两套推荐逻辑必然漂移，导致策划视图报告说的"下次内容"与 quest 实际生成的每日修复令不一致，报告失真。

summary 保持纯评估职责，专注"玩家学得怎么样"；quest 专注"下次玩什么"。策划视图的独特价值在诊断（哪些没掌握、为什么、补评依据、趋势），这是 quest 给不出的；处方层借 quest 现成输出即可。

summary → quest 是单向只读依赖，与 summary → voice/assessment 补评依赖同构。quest 不反向依赖 summary，直接读 Supabase 掌握度。

## 后果

策划视图报告需拼接两个服务的数据，实现上比单服务自包含复杂。但这是把职责切清楚必须付的代价，远好过推荐逻辑双写。
